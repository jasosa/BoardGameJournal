## Tech debt

- Library search, filters, sort and paging run in TypeScript over all of the person's copies (one query), and the Duplicate warning does the same. The service reads in pages of 1000 (the API row limit), so nothing is cut off. Fine for hundreds to a few thousand games. Move to SQL (indexed search, `limit/offset`) if a library grows past that. The mechanics filter and sorting by rating or last played wait for their data (L6, Phase 2). The filters panel is a collapsed `<details>` on every screen size; a bottom sheet on mobile belongs to the `oil-ui` pass.
- Auth config (`supabase/config.toml`): `[auth] enable_signup = false` blocks public sign-up; `[auth.email] enable_signup = true` is needed so password login works (false disables the whole email provider). The hosted Supabase project must match: "Allow new users to sign up" off, email provider on. Check before the first deploy. The allowlist mechanism is still to be chosen in F0.10.
- Accepted risk (2026-11-02): `npm audit` reports 17 moderate findings in dev dependencies. All come from one advisory, a `minimatch` denial of service (GHSA-g3hv-75wg-m249), pulled in by the ESLint toolchain. Dev only, not shipped. `npm audit --omit=dev` finds 0. Do not run `npm audit fix --force` (it downgrades eslint to 4.0.0). CI (F0.8) gates on `npm audit --omit=dev`. Revisit when `eslint` or `eslint-config-next` updates `minimatch`.
- Template defaults left out on purpose: `cacheComponents` and `partialPrefetching` in `next.config.ts`. Revisit when data fetching starts.

- UI gaps left from the F0.7 design review: no favicon (404 in console), no `loading.tsx`, `error.tsx` or `not-found.tsx`, no icons in the bottom nav. `--color-ink-faint` is 3.3:1 on paper in light, so use it only for non-text or large text.
- Dark token values are duplicated in `tokens.css` (explicit `data-theme` block and the media query block). Keep both in sync.
- shadcn/ui not set up yet. Add it when Quick Capture needs a sheet or dialog.


- Review leftovers (non-blocking): when storage lands, tie `game_images.storage_path` to a private bucket with a per-user prefix policy. If private games are ever shared, account deletion can fail on `collection_entries.game_id` (no action) when another user's collection references them; handle in the sharing ADR. The `supabase_admin` default privileges still grant `anon` on new objects created by that role; our migrations run as `postgres`, which is locked down.

- Login rate limit: Supabase counts sign-in attempts per IP, and the login action runs on our server, so the limit applies to the server, not the visitor. One abuser could lock the owner out, and there is no per-visitor brute-force limit. Add a per-IP/per-email limit in the action and a "too many attempts" message before hosting.
- Password rules: local `minimum_password_length` is 6. Raise to 12 or more before the password change and reset flow (ADR-0008).
- Duplicate titles only produce a warning (see Open questions). Near-matches (typos, "Catan" versus "Catan 5th Edition") are not detected, and existing duplicates are not merged.
- Library cards have no cover slot yet, no link to a game page, and no success cue after saving (the new card is the confirmation). No favicon (404 in the console), no `error.tsx` or `not-found.tsx` yet. Long titles clamp at 5 lines.
- Services are not marked `server-only` (callers pass the client in). Optional hardening.
- The proxy matcher skips paths ending in image extensions. `requireUser` must stay the real gate on any such route.

- L5 design notes (non-blocking, from the design review): the Library card shows the full title while the game page cover tile shows an initial; align when real covers arrive. Empty gap under "Add facts" when a game has no facts. Loading skeleton on the game page was not seen in a screenshot. Library card hover and reduced motion were not checked in a browser.
- The database limits players to more than 0 and play time to more than 0, while the form caps players at 99 and play time at 1440. A direct API write could store larger values on the user's own game. Harmless to others, so left as is.
- Status change stores only the current status. L3 adds dated history.

- Covers (L5b), known gaps recorded from the security review: (1) deleting a game or an account removes the `game_images` rows but not the files in the `covers` bucket; the account deletion and game deletion flows must remove `covers/{user_id}/...` first (or a sweep must run). (2) No per-user upload rate limit; the storage policy limits uploads to folders of the person's own games and 2 MB WebP files, but one person can still store many versions. Add a limit before other users arrive. (3) Failed removals of old files are ignored without logging, so orphans cannot be found. (4) `serverActions.bodySizeLimit` is 11 MB for every server action, not only uploads. (5) Animated WebP input keeps only the first frame; not covered by a test. (6) HEIC is not accepted; iPhones convert photos to JPEG when picking through the file input. (7) `game_images` policies do not yet tie `storage_path` to the owner; harmless while only the user's own session reads it, tighten if a service-role reader is ever added.
- Cover design notes (non-blocking, for the `oil-ui` pass): a card with a cover hides the title visually (screen readers still get it); real covers may lack readable text, so decide on a visible caption or overlay. The three text links under the title ("Add facts", "Replace cover", "Remove cover") read as clutter, and Remove has no confirmation or undo. No fallback if a cover image fails to load. The game page placeholder shows an initial while the Library tile shows the full title. Cover on the game page was widened to 192px on desktop.

- Status history: changes before L3 were never recorded, so each existing entry starts with one row dated from its creation. Backdating a change to before the game's own "Added" date is allowed on purpose. The list shows rows in the order logged, so dates can look out of order; a note on the page says so. After a successful status change the "Different date" disclosure stays open (could auto-close). The History section shows the latest 20 rows per copy. No composite key ties `collection_status_changes.user_id` to the entry's owner (only the two definer writers set it). A refused same-status change is silent.
- The service role and postgres can still delete entries and history rows by hand; only status changes are structurally guarded.

## Migration notes

- `20261104143330_archive_and_delete_entry.sql` (L4b): `collection_entries.archived_at` (with an index and a column update grant), `archive_entry` and `restore_entry` (security invoker), and `delete_entry` (security definer, returns jsonb `{result, paths}`). Rollback: `drop function public.add_game_copy(uuid, text, date);`. No data depends on it.
- `20261102183000_status_history.sql` (L3): new append-only table `collection_status_changes`, a trigger that writes the first row of each new entry, the function `change_entry_status(entry, status, date)`, closed direct updates of `collection_entries.status`, and a backfill (one row per existing entry, dated from its creation). Rollback: see the file header (drop the function, trigger and table; `grant update` on `collection_entries` again). No data depends on it that cannot be recreated.
- `20261102184000_status_history_hardening.sql` (L3 security review): `add_manual_game` gets an optional date (the old two-argument function is dropped), the first row uses that date, a guard trigger refuses status changes outside `change_entry_status`, owners can no longer delete entries through the API, and `set_updated_at()` is not executable by everyone. Rollback: see the file header.
- `20261102181000_covers_bucket.sql` (L5b): private `covers` bucket (WebP only, 2 MB), four `storage.objects` policies limited to the owner folder, and a unique index for one cover per game. Rollback: drop the policies and index, empty and delete the bucket. No data depends on it.

Rollback: restore plain checks, re-create the index without the `source <> 'manual'` condition, `grant update on public.games to authenticated`. When a feature needs another editable column, add it to the grant in a new migration. No data depends on any of this.
- `20261102124840_add_manual_game_function.sql` (F0.10): adds `add_manual_game(title, status)` (security invoker, authenticated only) and a 200 character limit on `games.name`. Rollback locally: drop the function and the `games_name_length` constraint, delete the file, `npx supabase db reset`. No data depends on it.
- `20261102103909_initial_schema.sql` (F0.9): creates `profiles`, `games`, `game_editions`, `game_images`, `collection_entries`, two functions and a trigger on `auth.users`. No data existed before.
